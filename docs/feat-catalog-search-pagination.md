# 레시피 카탈로그 서버 검색·페이지네이션

## 문제 상황

검색 화면이 `GET /api/v1/recipes`로 전체 카탈로그를 내려받은 뒤 제목과 설명만
앱에서 필터링했다. 레시피가 늘어날수록 응답과 화면 렌더링 비용이 커지고, 재료로는
검색할 수 없으며 한 화면에 결과가 모두 표시됐다.

## 검토한 대안

- 기존 전체 목록을 유지하고 앱에서 재료까지 필터링: 목록 응답에 재료가 없고 전체
  상세를 추가 조회해야 하므로 제외했다.
- 입력할 때마다 즉시 검색: 한글 조합 중에도 요청이 반복될 수 있어 명시적인 검색
  제출 방식으로 결정했다.

## 최종 결정

- 검색 화면은 `GET /api/v1/recipes/search`를 사용한다.
- 요리 이름(`title`)과 재료(`ingredient`)는 독립 입력이며 함께 입력하면 두 조건을
  모두 만족하는 결과를 요청한다.
- 페이지 크기는 9개로 고정한다.
- 처음, 이전, 다음, 마지막 이동을 제공한다. 이전·다음 5페이지 점프는 두지 않는다
  — 48dp 탭 타겟 일곱 개는 논리 폭 360dp 기기에서 한 줄에 들어가지 않아 마지막
  버튼이 다음 줄로 밀리는 문제가 실기기에서 확인됐다(2026-08-19 리뷰).
- 기존 `findAll()`은 홈 화면과 이전 앱 버전의 제목 기반 조리 세션 복원을 위해
  유지한다.

## 검증

- 검색 요청의 URL 인코딩, 사용자 헤더, 페이지 메타데이터 파싱 테스트
- 잘못된 검색 응답 형식 거부 테스트
- 제목·재료 제출, 5페이지 이동, 처음·마지막 이동, 조건 초기화 위젯 테스트
- `dart format --set-exit-if-changed`, `flutter analyze`, `flutter test`

## 이후 작업에서 지킬 것

- 검색 결과 개수는 현재 페이지 항목 수가 아니라 서버의 `totalItems`를 표시한다.
- 검색 조건을 바꾸거나 초기화하면 1페이지부터 다시 조회한다.
- 전체 목록 API의 응답 호환성을 깨지 않는다.
